Command Centre · Beta 0.1 Design

One browser.
Every agent, visible as it runs.

The Command Centre is the interface partners use to run a company through Spock end-to-end — from intake through to the finished IC paper — and watch every step happen on screen.

Six capabilities, in user-journey order

The Command Centre gives partners six things. They follow the natural shape of a run.

Gold border marks a capability that is interactive — a moment only you can action.

  1. 1
    Intake wizard

    Private or public company. Screener or full IC process. Upload everything from the data room — IM, deck, model, extracts. External sources (EODHD, filings) pull automatically. One button: run.

  2. 2
    Live audit treeHeadline feature

    As the run executes, every agent appears on screen — which one is active, what it is working on, and its output streaming in line by line. Collapsible, but nothing hidden. This is the headline differentiator over today's opaque CLI runs.

  3. 3

    Four human gatesInteractive

    Explicit and interactive. The run pauses at four moments — scope-lock, the taste board, the lever sheet, the final call. A decision only a partner makes. The run does not continue until you act.

  4. 4
    The paper, rendered

    When the IC paper is produced it renders in the canonical Spock pack format — in the browser. The same template, the same aesthetics. Not reprinted or reformatted; the live document.

  5. 5
    Yours
    Comment layerInteractive

    Highlight any text in the paper → leave a comment. Every comment carries a type toggle: systems · language · content · insight · other. Anchored to text so comments survive re-renders.

  6. 6
    Learning staging area

    Comments flow to a staging area where Spock evaluates the note, raises it to the right level of abstraction, proposes which doctrine or prompt to change, and serves it for your approval. On approval, it implements.

The headline differentiator

The live audit tree. Every agent, on screen, as it works.

Today's Spock runs happen in a terminal. Partners see output when a stage is done — a black box that occasionally prints results. The Command Centre replaces that with a live, structured view of the entire run.

Every time an agent fires — Forge, Champion, Crucible, the evidence specialists, the valuation trio, the AI-IC panel — it appears in the tree with its current status and its output streaming in real time.

Collapsible. Nothing hidden. "Much, much more detailed output as it runs" — the design brief verbatim.

The clever bit

The learning loop — capability 6 — closes the improvement cycle.

Comments on the paper are not just annotations. They are inputs to Spock's self-improvement engine. The loop has five steps, and it wires directly into the existing Learning Register and doctrine-as-code substrate — no new infrastructure.

  1. 1Comment

    Partner highlights text in the paper, leaves a comment, and picks a type: systems · language · content · insight · other.

  2. 2Evaluate

    A Spock learning-evaluator agent reads the comment and its anchored context, decides if it is a one-off fix or a general rule, and lifts it to the right level of abstraction.

  3. 3Propose

    Spock proposes a concrete action — which doctrine file, agent prompt, or template to change, and how.

  4. 4Approve

    The proposal lands in the staging area UI. Roger approves, or iterates with Spock on wording and scope.

  5. 5Implement

    On approval, Spock edits the doctrine or prompt, records the change in the Learning Register, and marks the cycle complete.

The "implement" step is a scoped file edit in bones/doctrine/ or the relevant agent prompt, plus a register entry in the v11 Learning Ledger. The Comment Centre does not reinvent the learning infrastructure — it wires into what is already built.

Technology stack

The same three ingredients as Gabrielle's stack — arranged around Spock's existing engine.

Next.js front end. FastAPI (Python) back end. Claude Agent SDK for orchestration. Streamed to the browser over SSE. The pipeline logic is preserved — what changes is the driver.

Frontend
Next.js · React · TypeScript

The four hard UI problems — live collapsible audit tree, interactive gates, beautiful paper render, and a Google-Docs comment layer — are all rich client state. React is where the mature libraries live.

Backend / API
Python · FastAPI

Spock's brain is already Python. FastAPI gives REST for intake, SSE for live agent streaming, file-upload for private docs, and a clean wrapper for the existing conductor and source fetchers.

Live stream
SSE — Server-Sent Events

Runs are one-directional firehoses. SSE is simpler than WebSockets, survives proxies, and auto-reconnects. Gates use a separate REST call — no full-duplex needed.

Orchestration
Claude Agent SDK (Python)

The pipeline logic is preserved. What changes is the driver: from the Claude Code harness to a FastAPI service with the Agent SDK, so a web server can start, instrument, and stream a run.

Persistence
SQLite (Beta 0.1)

One-publisher-at-a-time discipline already exists. SQLite is enough to ship. Migrate to Postgres if multi-partner concurrency demands it.

The one architectural decision that matters most

Today a run is fired through the interactive Claude Code harness — a person-in-the-loop terminal. The Command Centre needs a run a web server can start, instrument, and stream. Re-hosting orchestration as a Python service using the Claude Agent SDK — so the web app POSTs to start a run, structured events emit per agent, the browser subscribes over SSE, and a REST call resumes at each gate — is the largest lift in the whole build. It must be proven first, in Phase 0, before anything else is written.

Open questions

Five decisions to resolve before or early in the build.

Q1 — Where does it run?

RecLocal-only (localhost) for Beta 0.1. Sidesteps auth and hosting; matches one-run-at-a-time reality.

Q2 — Auth / multi-partner?

RecSingle-user (Roger) for Beta 0.1. No per-partner login until the model is proven.

Q3 — Concurrency — one active run or parallel?

RecSingle active run with a visible queue. Matches the existing one-at-a-time discipline.

Q4 — Does the existing conductor stay the source of truth?

RecYes. The service orchestrates the conductor; the conductor owns the pipeline sequence.

Q5 — EODHD / filings — VPS fetchers or direct calls?

RecReuse the existing VPS fetchers. No new data plumbing in Beta 0.1.
